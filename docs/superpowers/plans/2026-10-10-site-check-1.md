# Sicherheits-Check, plan 1 of 2 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The manual Sicherheits-Check works end to end on a site: profile, every catalogue check graded by the spec's evidence rules, the uploads probe, the `.htaccess` copy template, storage with purge and export, and the dashboard box in both dashboards — without monitoring and mail, which are plan 2.

**Architecture:** New module `inc/SiteCheck/` (Controller + Settings + AdminPage, plus focused classes for locations, grading, checks, probe, mutex, run storage and the box). Grading is pure PHP fed with *observations*; checks only observe. Browser checks are a small JS file that fetches bounded and posts observations back. The Custom Dashboard gets one filter, `sfx/custom_dashboard/widgets`.

**Tech Stack:** PHP 8.0–8.5 (WordPress, Bricks 2.4.2 public API), vanilla JS for the admin page; tests in plain PHP (`tests/*-test.php`) and Node (`tests/*-test.mjs`), both run by `./quality.sh`; `msgfmt` for the `.mo`.

**Spec:** `docs/superpowers/specs/2026-10-10-site-check-design.md` — read it in full before any task. This plan orders the work and names test situations; it does not restate the spec's rules. Where they differ, the spec wins.

No story is cited (unprofiled); gate floor 3.

## Global Constraints

- **Working directory:** the theme root `wp-content/themes/sfx-bricks-child`. Branch `feat/site-check` (exists, carries the spec).
- **Local PHP:** `PHP="${PHP:-$(command -v php || echo /Applications/MAMP/bin/php/php8.5.2/bin/php)}"`; battery `./quality.sh`. WP-CLI cannot reach the local DB — use `"$PHP"` plus `wp-load.php` for anything needing WordPress.
- **Commits:** each task ends with a `WIP: …` commit made exactly as `git commit -m 'WIP: <text>'` (review-gates.md Mechanics). The real message is written once, at the Gate-B closing act (Task 9).
- **PSR-4 case** (invariant 1): namespace `SFX\SiteCheck`, folder `inc/SiteCheck/`, file name = class name byte for byte.
- **Access** (invariant 2 and spec "Who can use it"): one predicate `Access::allowed(): bool` = `\SFX\AccessControl::can_access_theme_settings() && current_user_can('manage_options')`; every AJAX handler also checks the nonce `sfx_site_check` — reads included.
- **Escaping** (invariant 3) at the echo site; **strings** (invariant 4) in text domain `sfxtheme`, German translations in `languages/de_DE.po` → `.mo`.
- **Options** exactly as the spec's Storage table, all `autoload = no`; only the plan-1 ones are written in plan 1 (`settings`, `manual`, `items`, `probes`, `mutex`); the monitor/lock/baseline options are added to DataPurge now so plan 2 adds no purge change.
- **No module-to-module edge.** SiteCheck reaches CustomDashboard only through the filter name; it never names a CustomDashboard class. CustomDashboard never names a SiteCheck class. ImportExport, the catalogue that already names twelve modules' contracts (AGENTS.md), names SiteCheck's import callback (Task 1) — catalogue, not an edge.
- **Run context.** Every check call receives the issued run's immutable context `RunContext` (Task 2): run ID, profile, indexability paths, sitemap allow list, fallback theme, probe consent. No check reads live settings during a run.
- **Observations become facts, never stored contents.** A server observation holds names, sizes, matched signature names, setting values. A browser observation (status, type, headers, first 64 KB as text, first 512 bytes as hex) is sent once, to the observe endpoint of its own check, and turned there into **facts** (status class, signature names matched, header values the grade needs, redirect flag, truncation) — at most 2 KB per target. Grading reads facts only; the final save carries facts only, never bodies. Nothing is stored beyond the graded result (spec rule 7).
- **One option namespace.** Every SiteCheck option name **and cron hook name** comes from `Options::name(string $key)` / `Options::hook(string $key)` (`inc/SiteCheck/Options.php`); a live harness may override the prefix to a random `sfx_site_check_h<random>_` so it never touches the real options or the real cron events. SiteCheck's part of purge lives in `Purge::run()` (`inc/SiteCheck/Purge.php`), which `DataPurge::run()` calls; **no harness ever calls `DataPurge::run()`**.
- **No new Composer dependency.** No `.htaccess` is ever written. No request to a PHP file outside spec rule 6.
- **Harness rule** (AGENTS.md Don'ts): any live harness removes every fixture from one teardown path declared before the first fixture, and fails fatally on a wrong directory.

## Review Focus

1. **A shared host where `stat()` on some uploads subfolders is denied** — the check must say Nicht prüfbar for those, never Grün. Pinned in Task 2 (unknown disk row) and Task 3 (`php_files_uploads` with an unreadable folder).
2. **A site behind a cache that answers every unknown URL with the home page (`200`)** — no Rot and no Grün from status; Nicht prüfbar. Pinned in Task 2 (comparison `200` cases) and Task 4 (JS classifier).
3. **An admin clicking "Prüfen" twice in two tabs** — the older run's save is refused, the newer one stored; nothing mixed. Pinned in Task 6.
4. **A user with `manage_options` but not in `SFX_THEME_ADMINS`** (or the reverse) — no page, no box, every endpoint refuses. Pinned in Task 1 and Task 7.
5. **A log or backup file of several hundred MB** — the fetch stops at 64 KB, the page does not freeze, the result is graded from the bytes read. Pinned in Task 4 (JS bounded reader with an endless stream) and Task 3 (server reads first 4 KB only).
